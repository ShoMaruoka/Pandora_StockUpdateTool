## 前提（ここで置いている仮定）

次の仮定で書いている。違う場合は、この節を直してから実装に進む。

1. 利用者は、夜間に Amazon の出品者出荷の在庫数を合わせる社内担当者である。画面操作の再現はしない。
2. 実行場所は、常時起動の Windows サーバーである。タスク スケジューラで、ログオンしていなくても実行する。開始は月〜金の 16:00 とし、17:00 までには終わる想定である。土日・祝日・会社休業日は、在庫を取得せず、Amazon へも送らずに終わる（「営業日の判定」）。休業日に動くと業務上困るためである。運用が安定したあとに、1日の回数を増やすことがある。増やすときはこの仕様を更新する。どのサーバーで動かすかは未決。
3. 販売可能在庫は「卸の調整在庫＋ロジレスのフリー在庫」で、0未満にはしない。調整在庫は、横浜（120）・八尾（400）・八尾2（405）・西（110）・東（150）の合計を 2 で割り、Excel の `ROUNDUP`（小数0桁）と同じく切り上げた数である。福岡（180）は含めない。計算は夜間ジョブが行い、実行サーバーに Office は入れない。
4. 6桁などの Amazon 出品者SKUは、既存ツールの `parse_sku` で WebCD にする。7桁は見積番号として扱う。item Robot の CSV は読まない。
5. 数量が決まらない SKU は送らない。未一致を理由に 0 にはしない。7桁の出品者SKUは見積番号であり、「7桁の見積SKU」の規則で数量を決める。見積が読めないとき、または構成商品が在庫ビューに無いときは、その見積SKUを送らない。
6. 更新するのは出品者出荷（`DEFAULT`）の絶対数量だけである。FBA など、それ以外の出荷経路の数量は変えない。
7. 出品一覧は、出品レポートと出品 API の2つから取り、和集合にする。Amazon 側の出品は、新規も削除も担当者が事前に登録しているので、Amazon にある SKU を対象にすれば漏れない、という前提である。どちらで欠けを補い、どちらも使えない夜に止めるかは「出品一覧」の規則による。
8. 前回数量が 10 以上で、新しい数量が 80% 以上減っている SKU は、その SKU だけ送らない（急減）。前回数量が 9 以下の SKU は、0 になっても急減にしない。新しい数量が前回数量と同じ SKU は送らない（同数）。それ以外で数量が決まった SKU は送る。一部だけ送った夜は成功である。
9. 実行結果は Chatwork に通知する。部屋と API トークンは、認証フォルダ内の `chatwork.json` に置く。更新した SKU があるときは、完了メッセージと更新した商品だけの CSV を送る。急減で送らなかった SKU があるときは、件数と内訳 CSV を別の投稿で送る。`failed` とプロセスの異常終了は文章で知らせる。`--dry-run` では通知しない。
10. 認証ファイルには client_id、client_secret、refresh_token、seller_id が入っている。2026-09-29 に出品 5 件の読み取りは成功している。全件の SKU 形式の確認と、数量の書き込みは未実施である。

## Objective

Amazon の在庫反映だけを、夜間の1回の実行で終わらせる。

今の手作業のうち、Amazon に関係するのは次である。

1. 販売管理から在庫を出す。
2. ロジレスからフリー在庫を出す。
3. 全モール在庫更新ツールで、出品者SKUごとの数量を計算する。
4. 人が Amazon へアップロードする。

完成時の動きは次のとおりである。

1. 販売管理のビューとロジレス API から在庫を取る。
2. 既存と同じ規則で販売可能在庫を計算する。
3. Amazon の出品レポートと出品 API から、出品者SKUと今の出品者出荷数量を読み、和集合にする。
4. 急減の SKU だけ送らない。一覧が使えない夜は1件も送らない。
5. 数量が決まり、急減でない SKU だけ、出品者出荷の数量を API で更新する。
6. 監査ファイルを残す。

成功とは、担当者が翌朝に「送った件数」か「送らなかった理由」をログだけで判断できることである。楽天・Yahoo!・メルカリのアップロードは、これまでどおり人が行う。

## Code Style

既存の `engine.py` の `parse_sku`、`build_master`、`calc` をそのまま呼ぶ。在庫の解釈をジョブ側に複製しない。

送信してよいかは、1つの結果で表す。

```python
result = AmazonRun(
    action="sent",  # sent / failed
    listed=1200,
    sent=1100,
    skipped=20,
    held=80,  # 急減で送らなかった件数
    unchanged=900,  # 前回と同じ数量で送らなかった件数
    reason="",
)
```

- `action` が `failed` のとき、更新リクエストは 0 件である。急減があっても、それ以外を送った夜は `sent` である。送った件数が 0 でも、一覧が揃っていて失敗が無ければ `sent` である。
- `skipped` は、見積として数量が決まらない SKU や WebCD 未一致など、数量が決まらず送らなかった SKU 数である。見積SKUを送らないことは、その1件だけで、他のSKUの送信は止めない。
- `held` は、数量は決まったが急減のため送らなかった SKU 数である。他の SKU は止めない。
- `unchanged` は、数量は決まったが前回数量と同じため送らなかった SKU 数である。数量は絶対値で送るので、同じ値を送っても Amazon 上は変わらない。
- ログと例外メッセージに、トークン、シークレット、seller_id を出さない。

## 処理の流れ

0. 「営業日の判定」で今日が休業日なら、ここで終わる。以降の取得、送信、通知は行わない。
1. ロジレス API で商品コードとフリー在庫を取得する。
2. `dbo.VO0507在庫出力` から WebCD と倉庫別在庫を読む。調整在庫は「調整在庫」の式で計算する。確認用に、WebCD と調整在庫の CSV を `output` へ書く。
3. Amazon の出品レポートと出品 API 一覧を読み、「出品一覧」の規則で対象 SKU を決める。一覧が使えない夜は `failed` とし、送信しない。
4. 6桁などの出品者SKUは、`parse_sku` と `calc` で新しい数量を決める。7桁は「7桁の見積SKU」で決める。今の出品者出荷数量は、急減の比較に使う。数量が決まった見積SKUも、この急減判定の対象である。
5. 前回数量が 10 以上で、新しい数量が 80% 以上減っている SKU は、その SKU だけ送らない。数量が決まり、急減でも同数でもない SKU は送る。前回数量が 9 以下の SKU は急減にしない。新しい数量が前回数量と同じ SKU は送らない。監査では「送らない」になり、更新前数量と更新後数量は同じ値で残る。Chatwork の更新 CSV にも入らない。2026-10-15 の監査では、送る予定 1,958 件のうち 451 件が同数だった。2026-10-15 の監査では、急減 173 件のうち 161 件が 0 への更新で、前回数量 1〜3 が 104 件だった。割合だけで見ると、1 個売れて 0 になった SKU まで止まり、0 にすべき在庫が Amazon に残るためである。
6. 認証、販売管理、ロジレスのいずれかが失敗したとき、または「出品一覧」の規則で一覧が使えないときは `failed` とし、1件も送らない。
7. 監査 CSV に、出品者SKU、WebCD、商品名、更新前数量、更新後数量、送るかどうかを残す。商品名は出品 API の `itemName` を使い、API に無い SKU（レポートだけの SKU）はレポートの「商品名」を使う。このファイルを書いてから送信する。
8. `failed` でないとき、数量が決まり急減でも同数でもない SKU の出品者出荷数量を絶対値で送る。引数なしの実行が全件更新である。`--sku` のときは、その1件だけをこの規則で判定する。指定した SKU が急減なら送らない。他の SKU の急減は、指定した SKU を止めない。送信の途中で通信や認証のエラーが起きたら、残りの SKU は送らず `failed` にする。送ってしまった分の自動取消はしない。
   - Amazon が SKU 単位で更新を拒否した（応答が `ACCEPTED` 以外）ときは、その SKU だけを飛ばして続ける。拒否した SKU は `output/amazon_rejected_<日時>.csv`（出品者SKU、WebCD、商品名、更新前数量、更新後数量、理由）へ追記する。拒否が一晩に 20 件を超えたら、異常とみなしてそこで止め、`failed` にする。拒否があっても最後まで送った夜は成功である。`--sku` のときは、拒否されたら `failed` である。
   - 全件更新では、1件ごとに Amazon が更新を受け付けた（`ACCEPTED`）ことだけを確かめ、読み戻しはしない。読み戻しで反映を待つと、全件が時間内に終わらないためである。反映の確認は、翌晩の一覧で前回と同数（`unchanged`）になっていることと、抜き取りで行う。`--sku` のときは、最大 10 分読み戻す。Amazon が受け付けたのに 10 分の間に反映を確認できなかったときは、失敗にせず「完了（反映は未確認）」として通知し、終了コードは 0 にする。2026-10-21 の `534174x24` は、受け付けから反映まで 5〜14 分かかった。
   - 送れた SKU は、1件ごとに `output/amazon_sent_<日時>.csv`（出品者SKU、WebCD、商品名、更新前数量、更新後数量）へ追記する。途中で止まっても、どこまで送ったかが残る。
   - 商品タイプは、出品 API の一覧にあるものを使う。無い SKU（レポートだけの SKU）は、その SKU を1件読んで取る。
   - Amazon が「商品タイプが無効」（issue コード 4000003）で拒否したときは、汎用の商品タイプ `PRODUCT` で1回だけ送り直す。出品に古い商品タイプ名（例: `FOOD_AND_BEVERAGE`）が残っていると、今の日本のマーケットプレイスでは受け付けられないためである。2026-10-21 に `534174x24` で起きた。商品タイプ定義 API でも、`FOOD_AND_BEVERAGE` は `PRODUCT` として返る。
   - Amazon が呼び出し回数の制限（HTTP 429）を返したときは、待ってからやり直す（最大3回）。それでも失敗したら、その SKU で止めて `failed` にする。
   - 失敗の通知には、送った件数と、送らずに残った件数を書く。
9. 通知は「通知」の規則で送る。通知に失敗しても、送った Amazon の数量は戻さない。
10. 画面に出す内容は、すべて `output/logs/nightly_<日時>.log` にも書く。タスク スケジューラは画面の出力を残さないためである。想定外のエラーは、種類と止まった場所（ファイル、行、関数）だけを書き、エラーの中身は書かない。ログを書けないときも処理は止めない。

## 営業日の判定

起動の直後、ロジレスと販売管理の在庫を読む前に、実行サーバーの日付（ローカル時刻）で判定する。次のどれかに当たる日は休業日である。

| 条件 | 取得元 |
|------|--------|
| 土曜または日曜 | 日付から判定 |
| 国民の祝日（振替休日・国民の休日を含む） | `jpholiday` |
| 会社休業日 | `dbo.T007CM休業日.非営業日` に今日の日付がある |

- 祝日に営業する日は無い（2026-10-23 担当者確認）。祝日を営業日に戻す設定は持たない。
- `T007CM休業日` には、国民の祝日と会社独自の休み（年始、お盆など）の両方が入っている。2026-10-23 の確認では、2026年の平日の祝日 17 日はすべて `T007CM休業日` にもあった。それでも `jpholiday` と和集合にするのは、`T007CM休業日` の登録が遅れた年（2026-10-23 時点で 2027年は 0 件）にも祝日に動かないためである。
- クリスマス、節分などの行事は休業日にしない。`jpholiday` は法律上の祝日しか返さない。Google カレンダーの「日本の祝日」は行事を含み、ネット接続も要るため使わない。
- 土日はタスク スケジューラでも外すが、タスクの設定を誤って毎日にしたときのために、ツールでも判定する。
- `T007CM休業日` は SELECT だけで読む。接続には `sqlserver.json` を使う。

休業日のときは次のとおりにする。

- ロジレス、販売管理の在庫、Amazon、Chatwork には1件もリクエストしない。監査などの CSV も書かない。
- ログ（`output/logs/nightly_<日時>.log`）に `start …` と `skip 休業日（<理由>）` と `exit 0` を書く。理由は「土曜」「日曜」「祝日 <祝日名>」「会社休業日」のどれかで、複数に当たるときは最初の1つでよい。
- 終了コードは 0 である。Chatwork には投稿しない（2026-10-23 担当者確認）。
- `--dry-run` と `--sku` でも同じく判定し、休業日なら終わる。

`T007CM休業日` を読めない（接続や認証の失敗、テーブルが無いなど）ときは、休業日かどうかが分からない。休業日に動くと困るため、営業日とはみなさず `failed` にし、1件も送らない。終了コードはほかの `failed` と同じ 1 である。営業日の判定で Chatwork に投稿するのは、この場合だけである（2026-10-23 担当者確認）。文面は失敗の文章で、「休業日（T007CM休業日）を読めなかったため、在庫を更新していない」ことと、送った件数 0 件を書く。エラーの中身（接続先、ユーザー名など）は書かない。`--dry-run` のときは、ほかの通知と同じく投稿せず、ログと画面にだけ出す（2026-10-23 担当者確認）。土日と祝日は DB を読まずに判定できるので、それらの日は DB を読む前に `skip` で終わる。

`--force` を付けたときは、この判定をせずに処理の流れ 1 から動かす。ログに `force 営業日の判定をしません` を書く。タスク スケジューラには登録しない。

会社独自の休みが `T007CM休業日` に未登録のまま当日になると、その日は動く。ツールでは見分けられないので、販売管理の運用で前もって登録する。

## 出品一覧

出品者SKUは、次の2つから取る。

| 取得元 | 中身 | 欠けの見分け方 |
|--------|------|----------------|
| 出品レポート `GET_MERCHANT_LISTINGS_ALL_DATA` | 全出品を1ファイルで返す。見出しは日本語（出品者SKU、数量、フルフィルメント・チャネル、ステータスなど） | 全体件数の申告が無い。状態と前夜比で見る |
| 出品 API（Listings Items API の検索） | 20件ずつのページで返す。1回の検索は 1,000件で打ち切られるので、作成日で区切って読み直す | API が申告する全体件数（`numberOfResults`、宣言件数）と、取得した SKU 数を比べる。前夜比も見る |

それぞれ、次のすべてを満たすときに「使える」とする。

- レポート: 状態が `DONE` である。行数が、前夜のレポートの行数から 10% 以上減っていない。
- API: 取得した SKU 数が宣言件数と一致する。宣言件数が、前夜の API の宣言件数から 10% 以上減っていない。

宣言件数との一致は、その夜の読み取りでページが抜けたことを見つける。前夜比は、Amazon が申告する件数そのものが減ったことを見つける。前夜比は、レポートは前夜のレポートと、API は前夜の API と比べる。2つは停止中の出品の数え方などが違うので、混ぜて比べない。

2026-10-17 の突き合わせでは、2,151 SKU のうち 2,149 が一致した。`350980` は API にだけあり、API 上は出品中で数量 3 だった。`324657` は数量が1違い、レポート作成後の受注と見ている。レポートだけでも API だけでも漏れが出るので、和集合にする。

夜ごとの扱いは次のとおりである。

| レポート | API 一覧 | 対象 | 結果 |
|----------|----------|------|------|
| 使える | 使える | 和集合 | 通常どおり |
| 使える | 使えない | 和集合（API は取れた分） | 送る。API が使えなかった理由と件数を通知する。API にだけある SKU は、その夜は漏れることがある |
| 使えない | 使える | API だけ | 送る。レポートが使えなかった理由（状態、または前夜比の減少）を通知する |
| 使えない | 使えない | なし | `failed` |

API が使えない夜も、取れた分の SKU は和集合に入れる。不足は読み取りの抜けであり、取れた SKU の中身は正しいからである。レポートが使えない夜は、レポートの行は1行も使わない。

レポートの行数と API の宣言件数は、毎夜 `output` に記録し、次の夜の比較に使う。使えなかった夜の値は記録せず、前回使えた夜の値を残す。記録が無い初回は、前夜比を見ない。認証の失敗と、API の検索が HTTP エラーで止まったときは、上の表によらず `failed` である。

和集合の各 SKU は次のとおり扱う。

| SKU の場所 | 前回数量（急減の比較） | 送る前の確認 |
|------------|------------------------|--------------|
| 両方 | API の出品者出荷数量（読む時刻が後なので新しい） | なし |
| レポートだけ | レポートの数量。フルフィルメント・チャネルが `DEFAULT` の行だけを対象にし、FBA の行は使わない | なし |
| API だけ | API の出品者出荷数量 | その SKU を1件ずつ API で読み直す。出品が無い（404）、または出品者出荷の数量が無いときは送らない |

数量の決め方（`parse_sku`、`calc`、7桁の見積）と急減の規則は、どこから来た SKU でも同じである。

## 調整在庫

手作業の Excel M列と同じ式である。

```
=ROUNDUP(SUM(G2:K2)/2,0)
```

| 列 | 倉庫 | 倉庫CD |
|----|------|--------|
| G | 在庫横浜 | 120 |
| H | 在庫八尾 | 400 |
| I | 在庫八尾2 | 405 |
| J | 在庫西 | 110 |
| K | 在庫東 | 150 |

在庫福岡（L列、倉庫CD 180）は合計に入れない。在庫は他システムと共有しているため、合計の半分だけを EC 側の卸在庫にする。

倉庫在庫が 0 以上のとき、合計 5 なら調整在庫は 3、合計 4 なら 2、合計 1 なら 1、合計 0 なら 0 である。

## 出品者SKUの解釈

2026-09-29 に読んだ出品の例である。全件ではない。

| 出品者SKU | 解釈 |
|-----------|------|
| `307679` | 6桁。WebCD `307679` の販売可能在庫をそのまま使う。選択肢CSVでは、商品 `015694` のブルーのシステム連携用SKU番号と一致する |
| `263860` | 6桁。WebCD `263860` |
| `2003739` | 7桁。見積番号。得意先CD 300 の明細から、販売可能在庫の最小を使う |

数量が決まらない SKU は、Amazon 上の今の数量のまま残す。

## 7桁の見積SKU

7桁の出品者SKUは、販売管理の見積番号である。対象は EC サイト用の特殊な見積で、`T720見積.得意先CD` が 300 のものだけである。通常の見積の有効期限や WEB掲載では絞らない。

明細は `T721見積明細`、商品の WebCD は `T410商品` から取る。読み取りは SELECT だけである。既存ツールの見積構成マスター（必要数量で割る処理）は使わない。調整在庫と、調整在庫にロジレスのフリー在庫を足す式は、6桁SKUと同じものを使う。

対象行は、商品CDと WebCD がある行である。区分 2 の特価行も含む。次の商品CDは除く。

- `0010000000000`
- `0011000000000`
- `0020000000000`
- `0030000000000`

各対象行の販売可能在庫は、その WebCD の調整在庫にロジレスのフリー在庫を足した数である。0未満にはしない。明細の数量では割らない。ロジレスにそのコードが無いときは、足すフリー在庫を 0 とする。見積SKUの数量は、対象行の販売可能在庫の最小値である。監査の WebCD には、その最小になった商品の WebCD を残す。同じ最小が複数のときは、見積明細の行番号が小さい行を残す。

次のときは、その見積SKUを送らない。Amazon 上の今の数量は残す。

- 見積番号が無い
- 得意先CDが 300 でない
- 対象行が1件も無い
- 対象行の商品が `dbo.VO0507在庫出力` に無い

在庫ビューに行が無いことは想定外であり、在庫0とはみなさない。ビューに行があり、倉庫の合計が0の商品は、調整在庫0として最小値に使う。

## 通知

Chatwork のファイル投稿で、メッセージと CSV を1件の投稿にする。トークンと部屋IDは `{EC_INVENTORY_DIR}/chatwork.json` に置き、ログ、通知文、CSV、リポジトリには出さない。

| 結果 | 通知 |
|------|------|
| 更新した SKU がある | 完了メッセージと、実際に更新した商品だけの CSV |
| 急減で送らなかった SKU がある | 止めた件数と、その SKU だけの CSV。更新の投稿とは別にする |
| Amazon が拒否した SKU がある | 件数と、その SKU だけの CSV（理由の列つき）。ほかの投稿とは別にする。更新の CSV には入れない |
| 定番在庫以外の商品を 0 にした SKU がある | 件数と、その SKU だけの CSV。更新・急減の投稿とは別にする。「定番在庫以外で 0 にした SKU」の規則による |
| レポートか API の片方が使えず、もう片方で補った | 完了メッセージに、使えなかった側と理由（API の不足件数、レポートの状態、前夜比の減少）を書き足す |
| `failed`、プロセスの異常終了 | 文章。送った件数と理由を含める。急減の CSV は付けない |
| 更新した SKU が 0 件で、ほかに投稿が無い | 「更新 0 件」の完了の文章を1件送る。夜間ジョブが動いたことを毎朝確かめられるようにする |
| どの夜も | 最初の投稿の文面の最後に、処理時間（起動から投稿の直前まで。例: `処理時間 12分34秒`）を書き足す。`failed` と異常終了の文章にも書く |
| `--dry-run` | 送らない。送るはずだった投稿の CSV を、同じファイル名で `output` に保存し、文面を画面に表示する |
| `--sku` | 指定した1件の結果だけ。他の SKU の急減は通知しない |
| 休業日で終わった | 送らない。ログだけに残す（「営業日の判定」） |
| `T007CM休業日` を読めなかった | 失敗の文章。休業日を読めず在庫を更新していないことと、送った件数 0 件を書く（「営業日の判定」） |

Chatwork の1投稿に付けられるファイルは1つである。更新、急減、定番在庫以外で 0 にした SKU、Amazon が拒否した SKU は、それぞれ別の投稿にする。投稿の順はこの順である。どの夜も成功である。

CSV の列は、出品者SKU、WebCD、商品名、更新前数量、更新後数量である。更新の CSV は監査のうち送った行、急減の CSV は急減で送らなかった行、定番在庫以外の CSV はその規則に当たる行だけを書く。数量が決まらず送らなかった行、全出品の監査、WebCD 全体の調整在庫 CSV は添付しない。ファイルの上限は 5MB である。超えたときは、そのファイルを付けず、件数と上限超過を文章で送る。

### 定番在庫以外で 0 にした SKU

次のすべてに当たる SKU を一覧にする。

- その夜に実際に送った（監査の「送るかどうか」が「送る」）
- 更新前数量が 1 以上で、更新後数量が 0 である。0 から 0 は入れない
- 監査の WebCD の商品が、`dbo.T410商品` で `定番在庫 = 2`（定番在庫以外）である

7桁の見積SKUは、監査の WebCD（最小在庫になった構成商品）で判断する。`T410商品` に WebCD が無い商品と、`定番在庫` が 1 の商品は入れない。WebCD は数値として突き合わせる（先頭の 0 の有無を区別しない）。

`T410商品` は SELECT だけで読む。読むのは Amazon への送信のあとで、一覧の対象になりうる WebCD だけである。`--dry-run` でも読み、件数を表示する（投稿はしない）。読めなかったときは、一覧の投稿をせず、最初の投稿に「定番在庫を読めなかった」ことを書き足す。在庫の送信は止めず、戻さない。`--sku` のときは、指定した1件だけで判断する。

Amazon の更新が成功したあとに通知だけ失敗したときは、在庫の再送も取消もしない。通知の失敗はログに残す。

## Boundaries

- Always: 休業日かどうか分からない日は送らない。秘密情報をリポジトリとドキュメントに書かない。数量が決まらない SKU を 0 にしない。急減の SKU は送らない。`failed` のときは更新リクエストを 0 件にする。送信前に監査ファイルを書く。出品者出荷以外の数量を変えない。更新した商品と、急減で止めた商品は、別の CSV で通知する。通知の失敗で Amazon の数量を戻さない。
- Ask first: 調整在庫の式を変えること。急減の条件を変えること。実行時刻や1日の回数を変えること。パッケージの追加。SQL Server の接続方式。実行するサーバー。Chatwork の通知条件を変えること。楽天・Yahoo!・メルカリをこのジョブに足すこと。
- Never: item Robot の CSV を Amazon の対応表として読む。item Robot のライセンスキーを使う。メルカリ API を呼ぶ。認証失敗時に在庫を 0 で送る。レポートと API の両方が使えない夜に、一部だけ送る。秘密情報を Git へ入れる。この仕様の承認前に夜間ジョブを実装する。

## Success Criteria

- 販売管理とロジレスの取得から、Amazon の出品者出荷数量の更新までが、1回のタスク実行で終わる。
- item Robot のファイルが無くても、この処理は完了する。
- 6桁の出品者SKUは、対応する WebCD の販売可能在庫で更新される。
- 7桁の見積SKUは、対象行の販売可能在庫の最小で更新される。見積が読めない、または構成商品が在庫ビューに無い見積SKUは、実行後も Amazon 上の数量が実行前と同じである。
- WebCD に一致しない SKU は、実行後も Amazon 上の数量が実行前と同じである。
- 前回数量 10 以上で 80%以上の急減がある SKU は送らない。前回数量 9 以下の SKU は、0 への更新でも送る。急減でない SKU は同じ夜に送る。一部だけの送信は成功である。
- 新しい数量が前回数量と同じ SKU は送らない。1 でも違えば送る。
- レポートと API の片方が使えない夜は、もう片方で補って送る。両方とも使えない夜は、更新リクエストが 0 件である。前夜から 10% 以上減った側は、使えないとして扱う。
- API にだけある SKU は、読み直して出品が無ければ送らない。
- 監査ファイルに、出品者SKU、WebCD、商品名、更新前数量、更新後数量、送ったか止めたか、が残る。
- 更新した夜は、Chatwork に完了メッセージと、更新した商品だけの CSV（出品者SKU、WebCD、商品名、更新前数量、更新後数量）が届く。
- 急減で送らなかった SKU がある夜は、Chatwork に止めた件数と、その SKU だけの CSV が届く。更新の投稿とは別である。
- 定番在庫以外（`定番在庫 = 2`）の商品を 1 以上から 0 にした夜は、Chatwork にその件数と、その SKU だけの CSV が届く。更新・急減の投稿とは別である。
- `failed` とプロセスの異常終了の夜は、Chatwork に送った件数と理由の文章が届く。
- `--dry-run` の夜は、Chatwork への投稿が 0 件である。
- 土日・祝日・`T007CM休業日` の日は、ロジレス・販売管理の在庫・Amazon・Chatwork へのリクエストが 0 件で、終了コードが 0 である。ログに休業日の理由が残る。
- `T007CM休業日` を読めない平日は、Amazon への更新リクエストが 0 件で、Chatwork に「休業日を読めず在庫を更新していない」失敗の文章が届く。`--dry-run` では届かない。
- `--dry-run` 以外の夜は、更新が 0 件でも Chatwork に1件以上届き、最初の投稿に処理時間がある。
- ログとリポジトリに、トークン、シークレット、seller_id が無い。
- `--dry-run` では、Amazon への更新リクエストが 0 件である。
- 楽天・Yahoo!・メルカリへのリクエストは、このジョブから 0 件である。
