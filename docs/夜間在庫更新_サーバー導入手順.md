# 夜間在庫更新のサーバー導入手順

記録日: 2026-10-20  
更新日: 2026-10-23（開始を月〜金の 16:00 にした。休業日は動かない。「休業日の動き」を追加）。2026-10-20: exe で導入する手順に書き換え

夜間の Amazon 在庫更新を、1つの exe（`nightly_amazon.exe`）にして、常時起動の Windows サーバーに載せる手順である。exe は開発 PC で作る。サーバーに Python は要らない。

登録するのは `--dry-run` だけである。Amazon へ数量を送る全件更新への切り替えは、実装計画の Task 8 が終わったあとに行う。

今 `MARUOKA-PC` で動いている dry-run のタスクは、サーバーで動くのを確かめてから止める（手順 7）。

## 0. 事前に決めること

| 項目 | 内容 | 例 |
|------|------|----|
| サーバー | 常時起動の Windows サーバー（64 ビット） | （未決） |
| 実行ユーザー | タスクを動かすアカウント。パスワードの期限切れで止まらないものがよい | `ドメイン\svc_ecinventory` |
| 配置先 | exe、`settings.json`、`output\` を置くフォルダ | `D:\Tools\EC_Inventory` |
| 認証フォルダ | 認証 JSON を置くフォルダ。実行ユーザーと管理者だけが読めるようにする | `D:\Tools\ec_inventory_secrets` |

以下、例の値で書く。読み替えて使う。

## 1. 通信の確認

サーバーから次へ接続できる必要がある。プロキシやファイアウォールがある場合は、事前に許可を取る。

| 接続先 | 用途 |
|--------|------|
| 販売管理の SQL Server（通常 TCP 1433） | 在庫ビュー、見積、商品マスタ（`T410商品`）の読み取り |
| `https://app2.logiless.com` | ロジレスのフリー在庫 |
| `https://api.amazon.com` | Amazon の認証 |
| `https://sellingpartnerapi-fe.amazon.com` | Amazon の出品一覧、出品レポート、数量更新 |
| Amazon の出品レポートのダウンロード先（`*.amazonaws.com` の署名付き URL） | 出品レポートの本体 |
| `https://api.chatwork.com` | 結果の通知 |

## 2. 開発 PC で exe を作る

開発 PC（Python が入っている PC）で行う。

1. 初回だけ、ビルドに使うパッケージを入れる。

```
py -3 -m pip install pyinstaller openpyxl pyodbc
```

2. `tools\build_exe.bat` をダブルクリックする。コマンドなら次と同じである。

```
cd /d D:\development\Pandora_StockUpdateTool
py -3 tools\build_exe.py
```

3. 最初にテストが流れる。テストが失敗したときは exe を作らずに止まる。
4. 成功すると `dist\nightly_amazon.exe` ができる（約 27MB）。

`build\` と `dist\` は Git に載せない。

## 3. サーバーに SQL Server の ODBC ドライバを入れる

exe の中には ODBC ドライバが入らない。サーバーに、`sqlserver.json` の `driver` に書いた名前と同じドライバを入れる。開発環境は `ODBC Driver 17 for SQL Server`（64 ビット）を使っている。

入ったかどうかは、サーバーの PowerShell で次を実行して確かめる。

```
Get-OdbcDriver -Platform 64-bit | Select-Object Name
```

## 4. exe と設定ファイルを置く

1. 配置先 `D:\Tools\EC_Inventory` を作る。
2. `dist\nightly_amazon.exe` をコピーする。
3. コピーした exe を右クリックして「プロパティ」を開き、下に「許可する」（ブロックの解除）があればチェックを入れる。ネットワーク越しにコピーした exe は、ブロックされていることがある。
4. 開発フォルダの `tools\settings.example.json` を、配置先に `settings.json` という名前でコピーする。`EC_INVENTORY_DIR` を認証フォルダにする。

```json
{
  "EC_INVENTORY_DIR": "D:\\Tools\\ec_inventory_secrets"
}
```

配置先は次の形になる。`output\` は初回の実行で exe の横にできる。

```
D:\Tools\EC_Inventory\
  nightly_amazon.exe
  settings.json
  output\            （実行するとできる）
```

- exe は、自分と同じフォルダの `settings.json` を読み、自分と同じフォルダに `output\` を作る。開発フォルダの `tools\settings.json` は読まない。
- `settings.json` にはパスだけを書く。トークンやパスワードは書かない。
- 実行ユーザーに、配置先へ書き込む権限を付ける。前夜の件数（`output\amazon_counts.json`）もここに書く。

## 5. 認証ファイルを置く

1. 認証フォルダ `D:\Tools\ec_inventory_secrets` を作る。フォルダのアクセス権を、実行ユーザーと管理者だけにする。
2. 次の4ファイルを置く。中身は今 `MARUOKA-PC` で使っているものと同じである。チャットやメールには貼らず、ファイルのまま移す。

| ファイル名 | 用途 | 注意 |
|------------|------|------|
| `sqlserver.json` | 販売管理 | サーバーから同じ SQL Server に届くこと |
| `logiless_oauth.json` | ロジレス | **コピーではなく移動にする**（下の注意） |
| `amazon_spapi.json` | Amazon | |
| `chatwork.json` | Chatwork | |

3. 実行ユーザーに、このフォルダの**書き込み権限も**付ける。ロジレスのトークンを更新したとき、ツールが `logiless_oauth.json` を書き換えるためである。

**ロジレスの注意:** ロジレスのトークンを更新すると、新しいトークンが `logiless_oauth.json` に書き戻される。同じファイルの写しを `MARUOKA-PC` とサーバーの両方で使うと、片方が古いトークンのまま残り、ロジレスの読み取りで失敗するおそれがある。手順 7 で `MARUOKA-PC` のタスクを止めてから、ファイルを移す。

## 6. 手で動かして確かめる

実行ユーザーでサーバーにログオンし、コマンドプロンプトで次を実行する。

```
cd /d D:\Tools\EC_Inventory
nightly_amazon.exe --dry-run
echo %ERRORLEVEL%
```

1. 終了コードが 0 で終わる。出品レポートの作成を待つので、数分から30分ほどかかる。
2. 画面で次を確かめる。

| 表示 | 見ること |
|------|----------|
| `list report=True api=True union=…` | 出品レポートと出品 API の両方が使えたか |
| `action sent`、`planned …`、`unchanged …` | 送る予定の件数と、前回と同数で送らない件数 |
| `zeroed irregular N of M` | 定番在庫以外で 0 にする件数 |
| `notice …` | Chatwork に送るはずだった文面（dry-run では投稿しない） |
| `elapsed …` | 起動からの処理時間。本番では最初の投稿の最後に `処理時間 …` として書く |
| `audit …` | 監査ファイルの場所。**`D:\Tools\EC_Inventory\output\` の下になっていること** |

3. `D:\Tools\EC_Inventory\output\` に次ができている。

| ファイル | 内容 |
|----------|------|
| `amazon_audit_<日時>.csv` | 全出品の判定 |
| `adjusted_stock_<日時>.csv` | WebCD ごとの調整在庫 |
| `amazon_updated_<日時>.csv` など | Chatwork に付けるはずだった CSV |
| `amazon_counts.json` | 前夜比に使う件数 |
| `logs\nightly_<日時>.log` | 画面に出した内容と同じもの。タスク スケジューラで動かしたときも残る |

`echo %ERRORLEVEL%` は exe が終わってから表示されるので、`1` が出たときは実行中ではなく、失敗して終わっている。dry-run なので、Amazon へは送っておらず、Chatwork へも投稿していない。

失敗したときは、画面の最後の `失敗しました: …` か `reason …` の行を見る。トークンやパスワードは画面に出ない。よくある原因は次のとおりである。

| 表示 | 確かめること |
|------|--------------|
| `認証ファイルがありません: <パス>` | `settings.json` が exe と同じフォルダにあるか。`EC_INVENTORY_DIR` が認証フォルダを指しているか。そのフォルダにファイルがあるか |
| ODBC やドライバ、接続に関するメッセージ | 手順 3 のドライバ名が `sqlserver.json` の `driver` と同じか。サーバーから SQL Server に届くか（手順 1） |
| `Amazon へ接続できません`、`Chatwork へ接続できません` | 手順 1 の通信。プロキシの設定 |
| `トークン取得に失敗しました` | 認証 JSON の中身。ロジレスは手順 5 の注意 |
| `ModuleNotFoundError` など、種類の名前だけ | 開発 PC で作り直した exe を置いたか。開発者に画面を見せる |exe がすぐに消える、または起動できないときは、手順 4 のブロックの解除と、ウイルス対策ソフトの隔離を確かめる（「運用メモ」）。

テストはサーバーでは動かさない。手順 2 のビルドで、開発 PC で流している。

## 7. MARUOKA-PC のタスクを止める

`MARUOKA-PC` で、管理者のコマンドプロンプトから次を実行する。タスクは消さず、無効にしておく。

```
schtasks /Change /TN "ECInventoryAmazonDryRun" /DISABLE
```

止めたあとに、`logiless_oauth.json` をサーバーの認証フォルダへ移す（手順 5）。移したあと、手順 6 の dry-run をもう一度通す。

## 8. タスク スケジューラに登録する

サーバーで、管理者のコマンドプロンプトから次を1行で実行する。`/RP *` にすると、実行ユーザーのパスワードを聞かれる。パスワードはコマンドに書かない。パスワードを保存するので、ログオンしていなくても動く。

```
schtasks /Create /TN "ECInventoryAmazonDryRun" /TR "\"D:\Tools\EC_Inventory\nightly_amazon.exe\" --dry-run" /SC WEEKLY /D MON,TUE,WED,THU,FRI /ST 16:00 /RU "ドメイン\svc_ecinventory" /RP * /RL LIMITED /F
```

- exe は自分の場所から `settings.json` と `output\` を決めるので、「開始（作業フォルダ）」は空でも動く。
- 実行ユーザーには「バッチ ジョブとしてログオン」の権利が必要である。登録や実行で権限エラーが出たら、サーバーの管理者に付けてもらう。

続けて、タスク スケジューラの画面でこのタスクを開き、次を設定する。

| 場所 | 設定 |
|------|------|
| 全般 | 「ユーザーがログオンしているかどうかにかかわらず実行する」になっている |
| 設定 | 「タスクを停止するまでの時間」を 2 時間にする（初期値は 3 日） |
| 設定 | 「タスクが既に実行中の場合」は「新しいインスタンスを開始しない」 |

## 9. 予定時刻を待たずに確かめる

```
schtasks /Run /TN "ECInventoryAmazonDryRun"
schtasks /Query /TN "ECInventoryAmazonDryRun" /V /FO LIST
```

終わったあとに、`/Query` の「前回の結果」が `0` であること、`D:\Tools\EC_Inventory\output\logs\` に新しいログがあること、`D:\Tools\EC_Inventory\output\` に新しい監査ファイルがあることを確かめる。

| 前回の結果 | 意味 |
|------------|------|
| `0` | 成功。dry-run なので Amazon へは送っていない |
| `1` | 取得の失敗、または一覧が使えなかった。数量は送っていない |

次の平日の 16:00 の実行でも同じ結果になっていれば、導入は完了である。

## ツールを直したとき（exe の入れ替え）

1. 開発 PC で手順 2 をやり直し、新しい `dist\nightly_amazon.exe` を作る。テストが通らなければ exe はできない。
2. サーバーでタスクが実行中でないことを確かめる（16:00〜17:00 を避ける）。
3. 配置先の `nightly_amazon.exe` だけを置き換える。手順 4 のブロックの解除もやり直す。
4. `settings.json` と `output\` はそのまま残す。`output\amazon_counts.json` を消すと、次の夜は前夜比を見ない。
5. 手順 6 の dry-run で確かめる。

入れ替える前の exe は、`nightly_amazon_<日付>.exe` のように名前を変えて残しておくと、戻すのが簡単である。

## 引数と動き

**引数を付けずに起動すると、Amazon へ数量を送る（全件更新）。** 手で試すときは、必ず `--dry-run` を付ける。

| 起動のしかた | 動き |
|--------------|------|
| `nightly_amazon.exe --dry-run` | 送らない。Chatwork にも投稿しない |
| `nightly_amazon.exe` | 全件更新。送る SKU を1件ずつ送り、Chatwork に投稿する |
| `nightly_amazon.exe --sku 485706` | 指定した1件だけ送り、読み戻す |

## 全件更新を1回だけ試す（実装計画 Task 8 の確認）

16:00 の dry-run のタスクはそのまま残し、別の時刻に1回だけ動くタスクを登録する。毎晩の設定を変えないので、戻し忘れが起きない。

1. 全件更新に対応した exe（2026-10-20 以降に作ったもの）に入れ替える（「ツールを直したとき」）。
2. 前の営業日の 16:00 の dry-run の結果を見ておく。`planned`（送る予定の件数）が、全件更新で送る件数の目安になる。
3. サーバーで、管理者のコマンドプロンプトから次を1行で実行する。16:00 の dry-run と重ならないよう、18:00 にする。休業日（土日・祝日・会社休業日）は、このタスクもツールが何もせずに終わるので、営業日の日付にする。引数なしで動かすときに判定を飛ばしたいときだけ `--force` を付ける。日付（`/SD`）は実行する日にする。書き方はサーバーの日付の形式（日本語の Windows なら `2026/10/22`）に合わせる。

```
schtasks /Create /TN "ECInventoryAmazonFullOnce" /TR "\"D:\Tools\EC_Inventory\nightly_amazon.exe\"" /SC ONCE /SD 2026/10/22 /ST 18:00 /RU "ドメイン\svc_ecinventory" /RP * /RL LIMITED /F
```

4. タスク スケジューラの画面で、手順 8 と同じく「タスクを停止するまでの時間」を 2 時間にする。
5. 実行の後に、次を確かめる。

| 見るもの | 確かめること |
|----------|--------------|
| Chatwork | 「夜間在庫更新が完了しました。更新 N 件。… 処理時間 …」が届いている。N が前の営業日の `planned` に近い |
| `schtasks /Query /TN "ECInventoryAmazonFullOnce" /V /FO LIST` | 前回の結果が `0` |
| `output\amazon_sent_<日時>.csv` | 送れた SKU の一覧。行数が Chatwork の更新件数と同じ |
| `output\amazon_rejected_<日時>.csv` | Amazon が受け付けなかった SKU と理由（あった夜だけできる）。Chatwork にも別の投稿で届く |
| `output\logs\nightly_<日時>.log` | `sent N rejected N remaining N` の行。`remaining` が 0 なら最後まで送っている |
| セラーセントラル | 送った SKU を数件選び、出品者出荷の在庫数が `amazon_sent_*.csv` の更新後数量と同じ |
| 次の営業日の 16:00 の dry-run | `unchanged`（前回と同数）が大きく増え、`planned` が小さくなっている。送った数量が Amazon に反映された証拠になる |

6. 確認が済んだら、1回限りのタスクを消す。

```
schtasks /Delete /TN "ECInventoryAmazonFullOnce" /F
```

Amazon が一部の SKU だけを受け付けなかったときは、その SKU を飛ばして最後まで送る（前回の結果は `0`）。受け付けなかった SKU は、Chatwork の「Amazon が受け付けなかったSKUは N 件です」の投稿と `amazon_rejected_*.csv` で分かる。理由を見て、セラーセントラルなどで直す。直さなくても、次の晩にまた送ろうとするだけで、ほかの SKU は止めない。

通信や認証のエラー、または受け付けなかった SKU が 20 件を超えたときは、そこで止まる（前回の結果が `1`）。Chatwork の失敗の文章に「送った件数」と「未送信 N 件」が出る。送れた分は `amazon_sent_*.csv` に残り、送らなかった SKU は Amazon 上の数量が実行前のままである。送ってしまった分の自動の取り消しはしない。原因を直してから、もう一度1回限りのタスクで動かす（同数の SKU は送らないので、送れた分を二重に送ることはない）。

## 平日の全件更新へ切り替えるとき

上の確認が済んでから行う。16:00 のタスクの引数から `--dry-run` を外す。新しいタスクは作らない。

```
schtasks /Change /TN "ECInventoryAmazonDryRun" /TR "\"D:\Tools\EC_Inventory\nightly_amazon.exe\""
```

タスク名に「DryRun」が残るのが紛らわしければ、作り直してもよい。そのときは手順 8 の設定（停止までの時間など）もやり直す。

## 休業日の動き

土曜・日曜・国民の祝日・会社休業日は、ツールが何もせずに終わる。タスクは平日の毎日登録しておけばよく、祝日や休みの日にタスクを止めたり戻したりする必要はない。

- **判定**: 土日、`jpholiday`（法律上の祝日だけ。クリスマスなどの行事は入らない）、販売管理の `dbo.T007CM休業日` のどれかに当たる日が休業日である。
- **休業日の動き**: ロジレス、販売管理の在庫、Amazon、Chatwork へは何も接続しない。監査 CSV も作らない。ログ（`output\logs\nightly_<日時>.log`）に `skip 休業日（土曜／日曜／祝日 <名前>／会社休業日）` と `exit 0` だけが残り、タスクの「前回の結果」は `0` になる。Chatwork には投稿しない。
- **会社独自の休みは前もって登録する**: 年始やお盆などの会社の休みが `T007CM休業日` に入っていないと、その日は動いてしまう。ツールでは見分けられないので、販売管理の運用で前もって登録する。祝日は `jpholiday` が補うので、登録が遅れても祝日には動かない。
- **`T007CM休業日` を読めない平日**: 休業日かどうか分からないため、動かずに終了コード 1 で終わる。`--dry-run` 以外では、Chatwork に「休業日（T007CM休業日）を読めなかったため、在庫を更新していません」という失敗の文章が届く。販売管理の接続を確かめて、`--force` を付けずにもう一度動かす（`schtasks /Run`）。
- **休業日に手で動かしたいとき**: `nightly_amazon.exe --force` を付けると、判定をせずに動く。`--dry-run` や `--sku` と一緒に付けられる。タスク スケジューラには `--force` を付けて登録しない。
- **確かめ方**: 休業日の翌日に、その日のログが `start`、`skip 休業日（…）`、`exit 0` だけであることを見る。

## 運用メモ

- **ログ**: タスク スケジューラは画面の出力を残さないので、ツールが毎回 `output\logs\nightly_<日時>.log` を書く。中身は画面に出す内容と同じで、開始時刻と引数（`start …`）、最後の結果コード（`exit …`）、止まったときの理由（`失敗しました: …`）が入る。想定外のエラーでは、止まった場所（`at <ファイル>:<行> <関数>`）も入る。トークンやパスワードは書かない。ログが書けないときも、在庫の処理は止めない。
- ログに `start` だけがあり `exit` が無いときは、途中で強制終了された（「タスクを停止するまでの時間」を超えた、サーバーの再起動など）。

- **ウイルス対策ソフト**: PyInstaller で作った exe は、ウイルス対策ソフトに誤って隔離されることがある。起動しない、またはファイルが消えるときは、サーバーの管理者に配置先の除外を相談する。
- `output\` と `output\logs\` には営業日ごとにファイルが増える。古い監査ファイルとログは、期間を決めて手で消す。`amazon_counts.json` は消さない。
- 認証 JSON を差し替えたとき（Amazon のリフレッシュトークンの再発行など）は、手順 6 の dry-run で確かめる。exe の作り直しは要らない。
- 実行時刻や回数を変えるときは、仕様の「Ask first」に当たるので、先に仕様を直す。
