## Overview

Amazon の出品者出荷数量だけを、夜間の1回で更新する。卸の調整在庫は販売管理ビューから計算し、ロジレスのフリー在庫を足す。出品者SKUと今の数量は Amazon の出品APIから読む。item Robot のファイルは使わない。楽天、Yahoo!、メルカリはこのジョブから呼ばない。

最初に動くのは `--dry-run` である。監査ファイルまで作り、Amazon への更新は 0 件にする。全件の書き込みは、SKU形式の確認と、指定した1 SKU の読み戻しが済んでから行う。

## Architecture Decisions

- 6桁などの在庫解釈は `engine.py` の `parse_sku`、`build_master`、`calc` を呼ぶ。7桁は見積番号である。得意先CD 300 の明細から、販売可能在庫の最小を送る。既存の見積構成マスター（必要数量で割る処理）は使わない。見積が読めない、または構成商品が在庫ビューに無い見積SKUは送らない。
- 調整在庫は Excel の M列を読まない。倉庫 120、400、405、110、150 の合計を 2 で割り、0 から離れる方向へ切り上げる。倉庫 180（福岡）は入れない。
- ロジレスはフリー在庫 0 も含めて取る。既存の `tools/logiless_export_stock.py` は 1 以上だけなので、夜間ジョブでは全件を取る関数を別に置く。
- 急減の SKU だけ送らない。それ以外で数量が決まった SKU は同じ夜に送る判定にし、その夜は成功とする。認証、販売管理、ロジレス、一覧の欠落は `failed` で、更新リクエストは 0 件である。全件の Amazon 書き込みは Task 8 まで行わない。
- 送信は監査ファイルを書いた後だけ行う。途中で失敗したら残りは送らない。送った分の自動取消はしない。
- 更新対象は出品者出荷（`DEFAULT`）の絶対数量だけである。
- 秘密情報は `EC_INVENTORY_DIR` 配下の JSON だけに置く。パスは `tools/settings.json` で指定し、未指定時は `%USERPROFILE%\.ec_inventory\`。ログには出さない。
- SQL Server の接続文字列と Chatwork のトークン、部屋IDも同じフォルダに置く。パッケージの追加は、接続方式を確認してから行う。
- 更新した SKU がある夜は、完了メッセージと更新 CSV を1投稿にする。急減で送らなかった SKU がある夜は、件数と内訳 CSV を別投稿にする。`--sku` は指定した1件の結果だけ通知する。`failed` は文章だけである。通知に失敗しても Amazon の数量は戻さない。

## Dependency Graph

```
調整在庫と送信判断（外部接続なし）
    │
    ├── 販売管理の読み取り
    ├── ロジレスの全件読み取り
    └── Amazon 出品一覧の全件読み取り
            │
            └── dry-run（見積なし。Task 6 済み）
                    │
                    └── 見積明細の読み取りと最小在庫
                            │
                            └── dry-run（見積を含む。更新 0 件）
                                    │
                                    ├── 全件SKU形式の人手確認
                                    └── 1 SKU の書き込みと読み戻し
                                            │
                                            └── 全件書き込み
                                                    │
                                                    └── 結果通知とタスク登録
```

## Risks and Mitigations

| Risk                    | Impact | Mitigation                                                             |
| ----------------------- | ------ | ---------------------------------------------------------------------- |
| 6桁と7桁以外の出品者SKUが多い       | 高      | Task 6 で divide 362、multiply 1、manual 1 を確認した。書き込み前に、この規則のままでよいか人手確認する |
| 見積の構成商品が在庫ビューに無い        | 中      | その見積SKUだけ送らない。在庫0とはみなさない。他のSKUは止めない                                    |
| 一覧取得が途中で切れる             | 高      | 件数不一致は `failed` とし、1件も送らない                                             |
| 送信の途中失敗                 | 中      | 残りは送らない。送った分は監査に残し、自動では戻さない                                            |
| ロジレスのリフレッシュトークンが30日で切れる | 中      | 更新のたびに新しいトークンを保存する。失敗は Chatwork へ出す                                    |
| SQL Server へ書き込んでしまう    | 高      | SELECT だけにする。接続確認は Task 3 の前に行う                                        |
| 急減の SKU を送ってしまう         | 中      | その SKU だけ更新リストから外す。件数と内訳 CSV を Chatwork へ別投稿する。全件送信は Task 8 |
| Chatwork のファイル上限は 5MB    | 低      | 添付は更新した商品だけにする。超えたときはファイルを付けず、文章で知らせる                                 |
| 在庫更新のあとに通知が失敗する         | 中      | Amazon の数量は戻さない。通知失敗はログに残し、在庫の再送はしない                                    |
| 会社の休みが `T007CM休業日` に未登録 | 高 | ツールでは見分けられず、その日は動く。販売管理の運用で前もって登録する（2026-10-23 時点で 2026年の年末と 2027年は未登録）。祝日は `jpholiday` で補う |
| `T007CM休業日` が読めない平日 | 中 | 営業日とみなさず送らない。dry-run 以外は Chatwork に失敗の文章を出す。土日と祝日は DB を読まずに終わる |
